# ADR-012: MVP 모니터링은 Prometheus와 Grafana 기반 최소 관측 스택을 사용한다

## 상태

Accepted

## 배경

MVP 인프라는 ADR-008에 따라 EC2 1대, RAM 4GB, EBS 50GB, rootful Podman 기반으로 운영한다.

평시 컨테이너는 `readle-nginx`, `readle-frontend`, backend live slot 1개, MySQL, monitoring 도구로 제한한다. Redis는 ADR-007/ADR-008에 따라 기본 구성에서 제외했고, 백엔드 live slot은 배포 상태에 따라 `readle-backend-blue` 또는 `readle-backend-green`가 될 수 있으며 배포 시 반대 slot을 임시 기동한다.

현재 운영 host의 관측 구성은 다음과 같다.

- rootful Podman 5.7 / cgroup v2를 사용한다.
- backend health/readiness는 edge를 통해 공개되어 있고, `/api/actuator/prometheus`는 401로 보호된다.
- Micrometer Prometheus registry와 ADR-021의 custom business meter를 `/api/actuator/prometheus`로 제공한다.
- Prometheus, Grafana, exporter, Loki, Alloy는 rootful Podman Quadlet/systemd unit으로 운영한다. monitoring host port는 publish하지 않는다.
- container log backend는 journald이며, Podman JSON-file log rotation 정책은 현재 runtime과 맞지 않는다.

이 구조에서는 다음을 빠르게 확인할 수 있어야 한다.

- EC2 CPU, memory, disk, load, restart 상태
- 컨테이너별 CPU, memory, restart, OOM 징후
- backend health, latency, error rate, JVM 상태
- MySQL connection, availability, resource 상태
- MySQL backup 성공 여부
- frontend candidate 비라우팅 preflight 시 메모리 여유
- 배포 중 backend candidate 추가 기동 시 메모리 여유
- 부하 테스트 시 병목 지점

다만 단일 4GB EC2에서 로그/트레이싱/대시보드/알림을 모두 올리면 관측 도구가 서비스 자원을 잠식할 수 있다. 따라서 MVP에서는 필요한 최소 메트릭 관측과 가벼운 대시보드만 둔다.

## 결정

MVP 모니터링은 Prometheus와 Grafana 기반의 최소 관측 스택으로 구성한다.

EC2 내부에 다음을 rootful Podman 컨테이너로 실행한다.

- Prometheus
- Grafana
- node_exporter
- prometheus-podman-exporter
- mysqld_exporter
- Loki
- Alloy

cAdvisor는 이 host의 선택지에서 제외한다. 현재 runtime은 rootful Podman 5.x이고, container 지표는 Podman socket을 읽는 `prometheus-podman-exporter`로 수집한다.

backend는 Spring Boot Actuator의 health/readiness endpoint와 Prometheus metrics endpoint를 제공한다.

- `/api/actuator/health/readiness`
- `/api/actuator/prometheus`

`/api/actuator/prometheus`는 application boundary에서 인증을 유지한다. Prometheus private scrape는 root-only credential file을 사용해 구성하며, Public Nginx는 metrics path를 deny한다.

Prometheus는 active backend slot을 고정 hostname으로 직접 추정하지 않는다. Backend deploy helper는 edge cutover 성공 뒤 active blue/green backend hostname을 Prometheus file-SD target file에 atomic publish한다. Prometheus reload/watch 실패는 앱 배포 실패나 rollback 조건이 아니다.

Grafana는 운영자용 인증 dashboard로 사용한다.

- host port `3000`을 publish하지 않는다.
- 기존 Nginx HTTPS entrypoint의 `/grafana/` subpath로 접근한다.
- `root_url=https://<service-host>/grafana/`와 `serve_from_sub_path=true`를 사용한다.
- anonymous access와 self sign-up을 비활성화한다.
- bootstrap admin secret은 root-only 파일에 보관한다.
- 팀원은 개인 Viewer 계정을 사용한다.
- datasource는 Prometheus metrics와 Loki logs만 provisioning한다.
- 초기 dashboard는 2~3개로 제한한다.
- dashboard refresh interval은 30초 이상이다.
- 플러그인과 image renderer는 기본 금지한다.
- Grafana Live/WebSocket route는 MVP 범위에서 제외한다.

Prometheus는 단기 보관만 수행한다.

- `scrape_interval`: 30초
- `retention.time`: 3일
- `retention.size`: 512MB

로그 검색은 좁은 staged exception으로만 허용한다. Loki와 Alloy는 EC2-local,
private-only logging layer로 사용하고, public log port나 S3 log archive를 만들지
않는다. 현재 runtime은 journald를 사용하므로 `journald.conf.d` quota로 host log
보관량을 제한한다. Podman JSON-file `max-size`/`max-file` 정책을 적용했다고
문서화하지 않는다.

Loki는 single-binary filesystem storage로만 실행한다.

- 보관 기간: 7일, `168h`
- schema: TSDB filesystem schema `v13`
- index period: `24h`
- compactor `working_directory` 명시
- `retention_enabled=true`
- `delete_request_store=filesystem`
- `limits_config.retention_period=168h`

Loki retention은 Loki가 수신한 로그에만 적용한다. shipper outage, position loss,
journald overrun 이후 backfill은 보장하지 않는다. 7일 경과를 rollout에서 기다리지
않고, config와 compactor metric/log evidence로 acceptance를 판단한다.

Alloy는 host journald를 읽어 Loki로만 전달한다.

- `/var/log/journal`, `/run/log/journal`은 read-only mount만 허용한다.
- Podman socket은 mount하지 않는다.
- `loki.source.journal`은 rollout freshness 확인을 위해 `max_age=5m`를 사용한다.
- label은 low-cardinality allowlist만 사용한다.
- raw message body, URL, token, exception text, provider response는 label로 승격하지 않는다.
- obvious secret-bearing structured field는 drop/redaction한다.

Rollout acceptance는 marker query proof를 요구한다. `logger -t readle-log-probe`로
남긴 unique marker가 private Loki query에서 `120초` 안에 조회되고, 같은 window에서
Alloy journal-lines counter가 증가해야 한다.

Logging은 serving, backend deploy, MySQL backup에 대해 non-blocking이다. Backend
deployment script와 backend artifact는 Loki/Alloy를 위해 변경하지 않는다. Loki/Alloy
gate 실패 또는 OOM 발생 시 로그는 journald-only로 유지한다.

MVP 기본 구성에서 제외한다.

- Tempo
- Jaeger
- ELK/OpenSearch
- Grafana image renderer
- 장기 메트릭 보관
- 고가용 모니터링
- Alertmanager, webhook, pager 같은 외부 알림 전달
- custom business metric 계측 (ADR-021에서 채택으로 대체)
- Grafana Live/WebSocket proxy
- EC2 내부 부하 테스트

부하 테스트는 EC2 내부에서 실행하지 않는다. k6 같은 부하 발생기는 로컬 머신 또는 CI runner에서 실행하고, EC2의 Nginx/API로 외부 트래픽을 발생시킨다.

## 리소스 기준

Grafana 포함 metrics-only monitoring budget은 `896MB`를 기준으로 한다. Loki/Alloy를
enable한 monitoring+logging budget은 `1216MB`를 기준으로 한다.

| 대상 | 제한 |
| --- | ---: |
| Prometheus | 256MB |
| Grafana | 512MB |
| node_exporter | 32MB |
| mysqld_exporter | 32MB |
| prometheus-podman-exporter | 64MB |
| Loki | 256MB |
| Alloy | 64MB |

Loki와 Alloy를 enable하기 전 capacity gate를 통과해야 한다. live stack,
monitoring+logging stack, 실제 backend candidate를 함께 띄운 뒤 3분 안정화 구간을 거쳐 15분 동안 다음
조건을 모두 만족해야 한다.

- `MemAvailable >= 576MB`
- 분당 swap-in `<= 1MiB` (swap-out은 evidence만 기록)
- memory PSI `some`, `full`의 `avg10 < 0.10`
- 모든 sample의 5-minute load average `< 1.5`
- root filesystem 여유 `10GB` 이상 및 `20%` 이상
- OOM event 없음

조건을 통과하지 못하면 Loki/Alloy를 enable하지 않는다. 이 경우 로그는
journald-only로 유지하고, backend candidate 배포 경로와 MySQL backup은 변경하지
않는다.

평시 전체 EC2 메모리 예산은 다음을 기준으로 한다.

| 대상 | 제한 |
| --- | ---: |
| MySQL | 1024MB |
| backend live slot | 640MB |
| frontend | 192MB |
| nginx | 128MB |
| monitoring+logging 전체 | 1216MB |

평시 합계는 `3200MB`이며, 약 `896MB`를 host reserve로 둔다.

배포 중에는 backend candidate가 추가로 실행되므로 backend live slot/candidate limit을 각각 `640MB` 기준으로 둔다.

| 대상 | 배포 중 제한 |
| --- | ---: |
| MySQL | 1024MB |
| backend live slot | 640MB |
| backend candidate | 640MB |
| frontend | 192MB |
| nginx | 128MB |
| monitoring+logging 전체 | 1216MB |

backend candidate 배포 중 합계는 `3840MB`이며, 4GiB host에서 산술상 잔여 한도는 약
`256MB`까지 줄어드는 staged exception이다. cgroup hard cap은 예약량이 아니므로 이 값은
보장된 host reserve가 아니다. 이 값은 평시 계약이 아니며, 실제 enable 여부는 15분
capacity gate의 `MemAvailable >= 576MB` 실측으로 판단한다.

frontend-only 배포 중에는 `readle-frontend-candidate`를 비라우팅 preflight로 잠시 추가한다.

| 대상 | frontend 배포 중 제한 |
| --- | ---: |
| MySQL | 1024MB |
| backend live slot | 640MB |
| frontend live | 192MB |
| frontend candidate | 192MB |
| nginx | 128MB |
| monitoring+logging 전체 | 1216MB |

frontend-only 배포 중 합계는 `3392MB`이며, 4GiB host에서 산술상 잔여 한도는 약
`704MB`다. 이 역시 cgroup hard cap 합계일 뿐 보장된 host reserve는 아니다.

frontend/backend candidate 동시 배포는 지원하지 않는다.

현재 EC2 실측 기준으로 MySQL과 Nginx container limit은 아직 정책값 적용이 검증되지 않았다. 모니터링 rollout 전에 MySQL `1024MB`, Nginx `128MB` 제한을 canonical start path에서 먼저 적용/검증해야 한다.

배포 중 OOM 또는 memory pressure가 반복되면 다음 순서로 줄인다.

1. Loki/Alloy enable을 보류하고 로그는 journald-only로 유지한다.
2. Prometheus retention size/time을 축소한다.
3. dashboard refresh interval을 증가한다.
4. Grafana memory limit 축소 또는 외부 Grafana Cloud를 별도 의사결정으로 검토한다.
5. frontend/backend candidate 실행 시간 단축 또는 backend Blue-Green candidate 방식을 재검토한다.
6. EC2 인스턴스 증설을 검토한다.

## 보안 경계

Prometheus와 exporter는 host port를 publish하지 않는다. Prometheus는 `readle-private`에서만 scrape target과 통신한다.

Loki와 Alloy도 host port를 publish하지 않는다. Loki는 `readle-private`에서만 Grafana와
통신한다. Alloy는 journald read-only mount와 Loki push path만 사용하고, Podman
socket, host networking, TCP log receiver를 사용하지 않는다. Loki writable state와
Alloy positions state는 dedicated host path로 제한한다.

Grafana는 host port `3000`을 publish하지 않는다. Nginx만 `https://<service-host>/grafana/`를 Grafana container로 proxy한다. Nginx는 `Host`, `X-Forwarded-Proto`, `X-Forwarded-Host`를 보존하고 `/grafana/login`에 rate limit을 적용한다.

`prometheus-podman-exporter`는 rootful Podman socket을 사용한다. 이 socket 접근은 사실상 root-equivalent 권한이므로 Unix socket만 사용하고 TCP socket은 열지 않는다. Exporter는 fixed digest, `cap-drop=all`, `no-new-privileges`, 가능한 read-only filesystem으로 제한한다. 이 hardening이 host에서 성립하지 않으면 exporter를 우회해서 공개하지 말고 모니터링 component 선택을 재검토한다.

mysqld_exporter는 전용 least-privilege 계정만 사용한다. 계정은 `MAX_USER_CONNECTIONS 3`으로 제한하고 허용 권한은 `PROCESS`, `REPLICATION CLIENT`, `SELECT`만 둔다. root/application DB credential을 사용하지 않는다. Credential file은 root-only로 보관한다.

MySQL backup 지표는 node_exporter textfile collector에 안전한 값만 기록한다. 성공 여부와 마지막 성공 timestamp만 남기고 S3 bucket/key/secret label은 남기지 않는다.

## 이유

Prometheus는 단일 호스트의 메트릭 수집과 단기 저장에 충분하다. node_exporter는 EC2 host 상태를, prometheus-podman-exporter는 rootful Podman container 상태를, mysqld_exporter는 MySQL 상태를 관측한다.

Grafana는 Prometheus UI보다 팀 공유와 부하 테스트 결과 확인에 유리하다. 단, dashboard 수, refresh interval, plugin, image rendering을 제한하고 capacity gate를 통과하지 못하면 enable하지 않는다.

Loki와 Alloy는 journald-only보다 운영자 검색성이 좋고, 기존 Grafana `/grafana/`
surface를 그대로 쓴다. 단일 4GB EC2에서 로그 스택이 서비스 자원을 잠식하지 않도록
single-binary Loki, filesystem 7일 retention, private-only network, low-cardinality
label, 15분 capacity gate로 제한한다. Tempo, ELK/OpenSearch, tracing까지 함께 올리는
구성은 MVP 범위에서 제외한다.

부하 테스트를 EC2 내부에서 실행하면 서버 자원과 부하 발생기 자원이 섞여 결과 해석이 어려워진다. 따라서 부하 발생기는 EC2 외부에서 실행한다.

## 고려한 대안

### Prometheus만 사용

Grafana 없이 Prometheus UI만 사용하는 방식이다.

장점:

- 메모리 사용량이 가장 작다.
- 운영 컴포넌트가 적다.

단점:

- 팀 공유용 대시보드가 부족하다.
- 부하 테스트 결과와 배포 중 상태를 한눈에 보기 어렵다.
- 운영자가 PromQL에 익숙해야 한다.

결정: 거절한다. 다만 Loki/Alloy capacity gate 실패 시에도 Prometheus/Grafana
metrics-only monitoring은 유지하고, 로그만 journald-only로 둔다.

### Prometheus + Grafana + Podman exporter 사용

Prometheus로 수집하고 Grafana로 시각화하며, container 지표는 Podman socket 기반 exporter로 수집하는 방식이다.

장점:

- 팀원이 같은 dashboard를 기준으로 상태를 공유할 수 있다.
- 부하 테스트 중 latency, error, memory, MySQL 상태를 함께 볼 수 있다.
- rootful Podman 5.x runtime과 맞는 container 지표 수집 경로를 사용한다.

단점:

- Prometheus만 쓸 때보다 메모리 사용량이 증가한다.
- Podman socket 접근은 root-equivalent 잔여 위험을 가진다.
- dashboard/panel/refresh 설정을 제한하지 않으면 자원 사용량이 커질 수 있다.

결정: 선택한다.

### EC2-local Loki + Alloy journald 사용

Loki single-binary filesystem storage와 Alloy journald source를 사용하는 방식이다.

장점:

- 기존 Grafana `/grafana/` 경로에서 최근 로그를 검색할 수 있다.
- rootful Podman의 journald log backend와 맞는다.
- public log port, S3 log archive, HA 구성을 추가하지 않는다.
- Promtail EOL 경로를 새로 도입하지 않는다.

단점:

- 4GB EC2의 memory/disk pressure가 증가한다.
- filesystem Loki는 host 장애와 disk-full에 취약하다.
- shipper outage나 journald overrun 이후 backfill을 보장하지 않는다.

결정: staged exception으로 선택한다. 15분 capacity gate와 marker-query proof를
통과할 때만 enable하고, 실패하면 journald-only logging을 유지한다.

### Prometheus + Grafana + cAdvisor 사용

cAdvisor로 container 지표를 수집하는 방식이다.

장점:

- Docker 기반 예제가 많다.
- container metric dashboard 사례가 많다.

단점:

- 이 host의 기준 runtime은 Docker가 아니라 rootful Podman이다.
- Docker/privileged mount 중심 구성을 그대로 가져오면 실제 운영 형태와 어긋난다.

결정: 거절한다.

### 전체 LGTM 또는 ELK까지 도입

Grafana, Loki, Tempo, Prometheus 또는 ELK/OpenSearch를 HA/통합 관측 구조로 함께 운영하는 방식이다.

장점:

- 로그, 메트릭, 트레이싱을 통합해서 볼 수 있다.
- 장애 분석 범위가 넓다.

단점:

- 단일 4GB EC2에는 과하다.
- 저장소와 운영 컴포넌트가 크게 늘어난다.
- MVP의 주요 병목 확인 목적보다 비용이 크다.

결정: 거절한다.

### 외부 SaaS 관측 도구 사용

Grafana Cloud, CloudWatch, Sentry 같은 외부 서비스를 사용하는 방식이다.

장점:

- EC2 메모리와 디스크 부담이 줄어든다.
- 장기 보관과 알림을 쉽게 구성할 수 있다.

단점:

- 계정, 비용, 외부 연동 설정이 필요하다.
- 현재 AWS 권한과 네트워크 제약을 별도로 확인해야 한다.
- MVP 초기에는 자체 최소 스택보다 의사결정이 무거워질 수 있다.

결정: 별도 product/credential 결정 전까지 보류한다.

## 결과

MVP에서는 다음 dashboard를 우선 만든다.

1. Infra / Container Overview
   - CPU usage
   - memory usage
   - disk usage
   - network I/O
   - load average
   - container CPU/memory/restart/OOM 징후

2. Backend / MySQL / Backup Overview
   - backend health
   - HTTP request count/error/latency
   - JVM heap/non-heap memory
   - GC
   - thread count
   - datasource connection pool
   - MySQL connection
   - backup success boolean and last-success timestamp

Grafana Explore에서는 Loki datasource로 최근 7일 안의 backend, Nginx, MySQL,
Grafana 로그를 검색한다. 로그 dashboard는 초기 dashboard 2~3개 제한 안에서만
추가한다.

필요하면 dashboard 1개를 추가할 수 있지만, 초기 dashboard 총수는 2~3개를 넘기지 않는다.

부하 테스트는 k6를 EC2 외부에서 실행한다.

초기 테스트 단계는 다음을 기준으로 한다.

1. smoke: 1~2 VU
2. baseline: 5~10 VU
3. ramp: 10 -> 30 -> 50 VU
4. short stress: 병목 확인용 5~10분

부하 테스트 중 확인 지표는 다음이다.

- p95 latency
- 5xx rate
- backend memory
- JVM GC
- MySQL connection
- CPU load
- disk usage
- 배포 중 frontend 또는 backend candidate 추가 기동 시 OOM 여부

## 이행 상태

Prometheus·Grafana·exporter·Loki·Alloy container와 Quadlet/systemd unit, Prometheus scrape credential, public Nginx metrics deny, deploy helper의 active backend file-SD publish, MySQL backup textfile metric, Grafana dashboard·Loki datasource provisioning을 구현·적용했다.

Loki/Alloy initial rollout은 capacity gate와 marker-query proof를 통과해 적용했다. host 자원·이미지·logging 설정을 변경할 때는 같은 proof를 다시 수행한다.

MySQL과 Nginx resource cap은 canonical start path의 실제 적용 여부를 별도로 확인·유지한다.

## 재검토 조건

다음 조건이 생기면 모니터링 구조를 재검토한다.

- monitoring+logging 전체 메모리가 `1216MB` 안에 안정적으로 들어오지 않는다.
- Loki/Alloy capacity gate를 통과하지 못해 journald-only logging으로 남아야 한다.
- Prometheus retention 3일 미만으로도 디스크 압박이 발생한다.
- Loki retention 7일 안에서도 디스크 압박이 발생한다.
- 분산 tracing이 필요한 병목이 생긴다.
- Grafana dashboard 사용자 또는 panel 수가 증가한다.
- alerting이 운영 필수 요구가 된다.
- 단일 EC2 장애를 견뎌야 한다.

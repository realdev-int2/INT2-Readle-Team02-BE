# ADR-019: URL 크롤링은 Jsoup 기반 정적 파서로 유지하고, 실패 시 본문 직접 입력 Fallback UI로 대응한다

## 상태

Accepted

## 배경

현재 백엔드는 정적 HTML 파서인 `Jsoup`을 사용해 URL 크롤링 기능을 구현하고 있다. 실제 타겟 사이트를 대상으로 검증한 결과, 다음과 같은 도메인에서 크롤링이 실패하거나 본문이 빈 값으로 추출되는 현상이 확인되었다.

| 유형 | 대상 사이트 | 원인 |
| --- | --- | --- |
| Client-Side Rendering (CSR) | 네이버 D2, 카카오 기술블로그, MDN 일부 문서 | 초기 HTML에는 껍데기만 있고, 브라우저에서 JavaScript가 실행되어야 본문이 렌더링되는 순수 SPA 방식. JS 엔진이 없는 Jsoup으로는 본문 추출 불가 |
| 봇 차단(WAF) | 우아한형제들 기술블로그 | 강력한 봇 차단 방화벽이 크롤러 봇의 접근 자체를 `403 Forbidden`으로 차단 |
| 프레임 기반 렌더링 | 네이버 블로그(`blog.naver.com`), Spring Docs(구버전) | 본문을 `<iframe>`/`<frame>` 내부에 숨기는 방식. Jsoup은 프레임 내부 주소를 자동으로 따라 들어가 파싱하지 못해 제목 등 껍데기만 추출됨 |

반면 velog, tistory, 토스, 라인, 올리브영 등 정적 렌더링(SSR/SSG)을 지원하는 블로그는 정상적으로 본문이 추출된다.

이 문제를 구조적으로 해결하려면 Playwright, Selenium 같은 헤드리스 브라우저를 백엔드 서버에 도입해 JS 렌더링, 프레임 로딩 대기, 방화벽 우회를 처리해야 한다. 다만 이 경우 서버 메모리 리소스 소모, 크롤링 속도 저하, 인프라 세팅 비용이 크게 발생한다. 현재 프로젝트는 EC2 소형 인스턴스(4GB) 환경에서 운영 중이며, MVP 마감이 일주일 이내로 임박한 상황이다.

## 결정

크롤링 인프라를 헤드리스 브라우저 기반으로 전환하지 않고, **현행 Jsoup 기반의 정적 크롤러를 그대로 유지**한다.

대신 구조적·보안적 이유로 크롤링이 실패하는 사이트에 대해서는, 사용자가 본문을 직접 입력할 수 있도록 유도하는 **Fallback UI**를 명확히 제공하는 방향으로 스펙을 확정한다.

- 본문 추출 자체가 실패한 경우: "본문을 자동으로 가져오지 못했습니다. 본문을 직접 붙여넣어 주세요."
- 제목만 추출되고 본문 추출에 실패한 경우: "제목은 불러왔으나 본문을 추출할 수 없습니다. 본문을 직접 복사하여 붙여넣어 주세요."

크롤링 커버리지 확장(헤드리스 브라우저 도입 등)은 이번 MVP 범위에서 제외하고, 추후 운영 여건을 보고 별도로 재검토한다.

## 이유

- **일정**: MVP 마감까지 일주일이 채 남지 않은 상황에서, 크롤링 커버리지 확장보다 핵심 기능(콘텐츠 등록 → 검증 → 퀴즈 생성)이 안정적으로 동작하는 것에 리소스를 집중하는 것이 프로젝트 방향성에 부합한다.
- **인프라 제약**: EC2 소형 인스턴스 사양을 고려하면 헤드리스 브라우저 구동 시 메모리 부족(OOM)으로 이어질 위험이 크다. 정적 파서 대비 리소스 소모가 크고, Redis 없이 DB 기반으로 운영 중인 현재 아키텍처와도 부담 수준이 맞지 않는다.
- **비용 대비 효과**: 헤드리스 브라우저 도입은 JS 렌더링/프레임 로딩 대기/방화벽 우회까지 각각 별도 처리가 필요한 큰 작업이며, 이 시점에 투입하기엔 오버엔지니어링에 해당한다. 크롤링 실패 시에도 사용자가 텍스트를 직접 입력하는 대체 경로가 이미 존재하므로, 서비스의 핵심 학습 루프(콘텐츠 → 퀴즈) 자체는 계속 정상 동작한다.
- **팀 합의**: 관련 논의에서 팀원 전원이 동일한 방향(Jsoup 유지 + Fallback UI 강화)에 동의하였다.

## 고려한 대안

1. **헤드리스 브라우저(Playwright/Selenium) 도입**
    - 장점: CSR, 프레임 기반 렌더링 사이트까지 대부분 커버 가능
    - 단점: 서버 메모리 소모 급증(소형 EC2 환경에서 OOM 위험), 크롤링 속도 저하, 인프라 세팅 비용 발생, 남은 일정 내 검증까지 마치기 어려움
    - 기각 사유: MVP 마감 임박, 인프라 사양 제약
2. **일부 사이트만 개별 대응(예: 특정 도메인에 한해 프레임 내부 URL을 수동으로 파싱)**
    - 장점: 헤드리스 브라우저 도입 없이 일부 커버리지 개선 가능
    - 단점: 사이트별 예외 처리가 늘어나 유지보수 부담 증가, 대상 사이트가 늘어날수록 확장성 없음
    - 기각 사유: 이번 논의에서 별도로 채택되지 않았으며, 필요 시 향후 검토 대상으로 남겨둠
3. **크롤링 실패 시 아무 안내 없이 빈 값 반환**
    - 장점: 구현 비용 없음
    - 단점: 사용자가 실패 원인을 알 수 없어 학습 루프 진입 자체가 막힘
    - 기각 사유: 최소한의 UX 보완조차 없어 서비스 이용성이 크게 저하됨

## 결과

- 크롤링 성공 도메인(velog, tistory, 토스, 라인, 올리브영 등 SSR/SSG 지원 사이트)은 기존과 동일하게 자동 추출을 지원한다.
- CSR, WAF 차단, 프레임 기반 렌더링 사이트는 크롤링이 실패하며, 이 경우 사용자에게 Fallback UI(본문 직접 입력 안내)를 제공한다.
- 크롤링 실패/부분 실패 상태를 프론트에서 구분해 서로 다른 안내 메시지를 노출해야 하므로, 관련 API 응답에 실패 유형(본문 전체 실패 vs 제목만 성공)을 구분할 수 있는 필드가 필요하다.
- 크롤링 커버리지 확장(헤드리스 브라우저 등)은 MVP 이후 운영 데이터(실제 실패율, 사용자 요청 빈도 등)를 근거로 재검토한다.

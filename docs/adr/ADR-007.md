# ADR-007: MVP 인증 토큰은 JWT Access Token과 MySQL Refresh Token을 사용한다

## 상태

Accepted

## 배경

MVP 인증은 Kakao, Google OAuth 로그인을 전제로 한다. 폼 기반 기본 로그인/회원가입은 MVP 범위에서 제외되어 있으며, OAuth callback 이후 Readle 서비스에서 사용할 인증 토큰 정책이 필요하다.

초기 논의에서는 서버 session 저장소, 무상태 JWT, Redis 기반 Refresh Token 저장을 검토했다. 그러나 MVP 인프라는 RAM 4GB 단일 EC2에서 MySQL, backend, frontend, Nginx, 모니터링을 함께 운영해야 한다. Refresh Token만을 위해 Redis를 상시 운영하면 메모리와 장애 지점이 늘어난다.

따라서 MVP에서는 Access Token 인증은 JWT로 무상태 처리하고, 갱신/로그아웃에 필요한 Refresh Token 상태만 이미 운영하는 MySQL에 저장한다.

## 범위

이 ADR은 OAuth callback 이후 토큰 발급, Access Token 검증, Refresh Token 저장/갱신, Refresh Token cookie, 로그아웃/session 확인, 사용자 소유 리소스 authorization 원칙을 다룬다.

RBAC/admin 정책, 다중 기기 session UX, 강제 global logout, provider별 OAuth 앱 설정 세부값은 MVP 범위 밖이다.

## 결정

MVP 인증은 JWT Access Token과 MySQL 기반 Refresh Token을 사용한다.

- Access Token은 JWT로 발급하고 TTL은 30분으로 둔다.
- Refresh Token은 MySQL에 hash 형태로 저장하고 TTL은 14일로 둔다.
- 클라이언트는 Refresh Token을 HttpOnly cookie로 보관한다.
- 서버 session 저장소는 두지 않는다.
- Redis는 MVP 기본 인프라에서 제외한다.
- Access Token denylist/blacklist와 강제 폐기 API는 MVP 범위에서 제외한다.
- 로그아웃 시 현재 Refresh Token row를 폐기하고 Refresh Token cookie를 삭제한다.
- 만료된 Refresh Token은 cleanup job으로 정리한다.

## OAuth callback 보호

- provider allowlist는 `kakao`, `google`만 둔다.
- provider/app 설정의 redirect URI는 정확히 일치하는 값만 허용한다. wildcard, 동적 open redirect, 알 수 없는 provider callback은 거부한다.
- OAuth callback은 MySQL-backed one-time `state`로 CSRF를 방어하고 S256 PKCE를 사용한다. signed/stateless fallback은 두지 않는다.
- `state` 불일치, 만료, 재사용은 토큰 발급 없이 실패 처리한다.
- OAuth 교환이 실패하면 member·token을 만들지 않고 안전하게 실패 처리한다.
- OAuth state는 `oauth_authorization_state`에 state hash, provider, 상대 `return_to`, application-encrypted `code_verifier_ciphertext`, 만료·사용·생성 시각을 저장한다. `returnTo`는 외부 URL을 허용하지 않고 상대 path와 선택적 query만 허용하며, query를 제외한 path는 `OAUTH_ALLOWED_RETURN_PATHS`의 Spring-style allowlist pattern과 매칭한다(예: `/`, `/dashboard`, `/quizzes/**`; `/**` 단독 전체 허용은 금지). 없는 값과 scheme·authority·host·fragment, `//`, backslash, CR/LF, 인코딩 우회가 있는 값은 path를 `/`로 정규화하며, 허용된 query는 보존한다.
- callback은 unique state hash와 provider, `used_at IS NULL`, 미만료 `expires_at` 조건으로 원자적으로 한 번만 consume한다. verifier는 callback의 PKCE code exchange에만 복호화하며 반환하거나 로그에 남기지 않는다.
- 현재 `OAuthStateService`는 성공 consume 시 state row를 즉시 삭제하고, callback 조회에서 만료 state를 발견한 경우에도 삭제한다. 이 경로는 `code_verifier_ciphertext`를 함께 제거하며 이미 적용되어 있다.
- callback이 다시 오지 않은 만료 state의 주기적 물리 cleanup은 아직 적용하지 않았다. 후속 application cleanup job이 이를 책임지며, 그 전까지 state 유효성은 삭제 여부가 아니라 `expires_at`과 `used_at` 규칙으로 판단한다. state row는 member 생성 전에도 존재하므로 member FK를 두지 않는다.

### OAuth Provider Callback Config

MVP backend callback path는 provider별로 고정한다.

| Provider | Callback path |
| --- | --- |
| Kakao | `/api/auth/kakao/callback` |
| Google | `/api/auth/google/callback` |
- `provider` path variable은 allowlist(`kakao`, `google`) 기반으로만 처리한다.
- 알 수 없는 provider의 OAuth 시작/콜백 요청은 토큰 발급 없이 실패 처리한다.
- OAuth provider console에는 환경별 backend origin과 callback path를 조합한 exact redirect URI만 등록한다.
- ADR-007은 literal local/production full redirect URI 값을 소유하지 않는다. 실제 origin 값은 배포/환경 설정에서 관리한다.
- 사용자 입력값으로 redirect URI를 동적으로 만들지 않는다.
- callback 이후 frontend 이동이 필요하면 위 `returnTo` 검증을 통과한 서버 관리 allowlist path로만 이동한다.
- Production은 Edge Nginx가 frontend와 `/api`를 같은 origin으로 라우팅하고, 개발은 Vite proxy가 `/api`를 backend로 전달한다. callback landing은 token-free이며, client는 기존 `POST /api/auth/refresh`로 bootstrap하고 Access Token은 메모리에만 보관한다.
- OAuth client id/secret, Refresh Token 원문, provider token 원문, state 원문, `code_verifier_ciphertext`, Access Token은 문서와 로그에 남기지 않는다.

## Access Token 정책

Access Token은 HS256으로 자체 발급하며, 일반 API 요청에서 서버 session이나 DB token store를 조회하지 않는 stateless JWT로 검증한다. issuer와 signing secret은 환경 설정으로 주입하며 literal 값으로 문서화하지 않는다.

필수 검증:

- `alg`
- signature
- 고정 audience claim인 `aud=readle-api`
- `exp`
- `nbf`가 있으면 `nbf`
- issuer claim인 `iss`
- subject claim인 `sub`를 `member.uuid`로 매핑

Access Token은 로그아웃 후에도 만료 전까지 유효할 수 있다. MVP에서는 30분 TTL과 Refresh Token 폐기로 이를 수용하며, access-token denylist는 도입하지 않는다.

## Refresh Token 저장 정책

Refresh Token 원문은 저장하지 않고 random token의 hash만 MySQL에 저장한다. 기본 테이블은 다음 필드만 요구한다.

```sql

member_refresh_token (
  id,
  member_id,
  token_hash,
  expires_at,
  revoked_at,
  created_at
)
```

- `token_hash`는 unique로 둔다.
- `revoked_at IS NULL`이고 `expires_at`이 지나지 않은 row만 유효하다.
- `last_used_at`은 감사/디버깅 필요가 확인될 때만 선택적으로 추가한다.
- successor-chain, `replaced_by_token_id` 같은 추적 필드는 기본값으로 두지 않는다.

## Refresh Token rotation

MVP에서는 Refresh Token rotation을 적용하지 않는다.

기본 MVP 정책은 로그아웃/만료/취소 외 replay detection을 제공하지 않는다. rotation 미적용 시에는 짧은 Access Token TTL, HttpOnly/Secure cookie, hash 저장, logout revoke, cleanup job으로 위험을 줄인다.

유효하지 않은 Refresh Token은 인증 실패(Authentication failure)만 반환한다. 잘못된 토큰 제출로 인해 특정 member의 active Refresh Token을 일괄 폐기하지는 않는다.

기본 schema에 successor-chain 필드는 추가하지 않는다.

## Cookie 정책

Refresh Token cookie 기본값:

- `HttpOnly`
- `Secure`
- `SameSite=Lax` (기본값)
- `Max-Age`는 14일 Refresh Token TTL과 맞춘다.

`SecurityConfig`는 순서 있는 auth/cookie CSRF 체인(`/api/auth/**`)을 먼저 적용하고, Bearer API 체인(`/api/**`)에는 CSRF를 적용하지 않는다. 명시적 `/**` fallback으로 미매칭 요청의 우회를 막으며, 향후 cookie 기반 상태 변경 경로는 auth 체인에 배치하고 테스트한다.

cookie 이름은 가능하면 `__Host-readle_refresh_token`을 사용한다. 정확한 feasibility rule은 `__Host-` + `Secure` + `Path=/` + no `Domain`이다. 더 좁은 `Path`가 필요해 `Path=/`를 쓸 수 없으면 `__Host-`가 아닌 이름을 사용한다.

## 로그아웃과 session 확인

로그아웃은 현재 Refresh Token row를 `revoked_at`으로 폐기하고 Refresh Token cookie를 삭제한다.

Access Token은 stateless이므로 로그아웃 직후에도 만료 전까지 API 인증에 성공할 수 있다. 이는 MVP에서 수용한 동작이며, 즉시 강제 폐기가 필요해질 때 access-token denylist 또는 session/token store를 재검토한다.

`/auth/session`은 public bootstrap 상태 확인 endpoint다. 별도 서버 session 저장소나 Access Token 검증 없이, 현재 요청의 Refresh Token cookie가 active·unrevoked·unexpired인 경우에만 `authenticated=true`와 `member.uuid`를 반환한다. 보호 API 인증은 계속 Bearer JWT가 담당한다.

## RDB ownership authorization invariant

JWT는 호출자의 인증 identity를 증명할 뿐, 리소스 접근 권한을 단독으로 보장하지 않는다.

보호 리소스 접근은 먼저 JWT의 `sub`(=`member.uuid`)를 기준으로 리소스 소유자와 RDB에서 일치 여부를 확인한다. ownership 검증이 완료되면 내부 처리 단계에서 `member_id` FK를 사용해 service/SQL을 수행한다.

RBAC/admin abstraction은 관리자 또는 역할 요구사항이 실제로 생길 때 도입한다.

## 고려한 대안

### 서버 Session 기반 인증

강제 로그아웃과 session 폐기는 단순하지만, 서버 session 저장소가 필수이고 MVP API/OAuth 흐름에 비해 상태 관리가 커진다.

### JWT Access Token만 사용

구현은 가장 단순하지만 사용자가 자주 재로그인해야 하며, 로그아웃 이후 Access Token 만료 전까지 서버가 폐기를 통제하기 어렵다.

### JWT Access Token + Redis Refresh Token

Refresh Token TTL 관리는 단순하지만 Redis 운영 컴포넌트와 메모리 사용량이 추가된다. 단일 4GB EC2 MVP 기본 구성과 맞지 않는다.

### JWT Access Token + MySQL Refresh Token

Redis 없이 Refresh Token 폐기와 만료 상태를 서버가 통제할 수 있다. Refresh Token 재발급 시 DB 조회가 필요하고 cleanup job이 필요하지만, MVP에서는 기존 MySQL 운영 범위 안에서 감당 가능한 비용이다.

## 결과

MVP에서는 JWT Access Token과 MySQL Refresh Token 조합을 채택한다. 일반 API 인증은 stateless로 유지하고, 로그아웃/갱신에 필요한 상태만 MySQL Refresh Token row에 둔다.

API 문서에는 인증 endpoint와 흐름만 얇게 남기고, 토큰 TTL, 저장소, cookie, OAuth callback 보호, authorization 원칙은 이 ADR을 기준으로 관리한다.

추후 다음 요구가 생기면 토큰 정책을 재검토한다.

- RBAC/admin 또는 역할 기반 권한 정책이 필요한 경우
- 다중 기기 session 관리 UX가 필요한 경우
- forced global logout 또는 즉시 강제 폐기가 필요한 경우
- provider-specific OAuth 정책이 필요해지는 경우
- Refresh Token replay hardening이 필요해 rotation을 채택해야 하는 경우
- Refresh Token 조회/갱신이 MySQL bottleneck을 만드는 경우

그 시점에는 Redis, 별도 session/token store, access-token denylist, provider별 ADR 분리 여부를 새 ADR로 검토한다.

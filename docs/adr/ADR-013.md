# ADR-013: 퀴즈 생성 요청과 퀴즈 데이터를 `quiz_set`에서 통합 관리한다

## 상태

Accepted

## 배경

현재 Readle의 `quiz_set` 테이블은 콘텐츠 기반 AI 퀴즈 생성 과정과 생성 완료된 퀴즈 데이터를 함께 관리하고 있다.

현재 구조:

```
quiz_set
 ├─ content_id
 ├─ status (GENERATING / COMPLETED / FAILED)
 ├─ question_count
 ├─ created_at
 ├─ completed_at
 ├─ is_bypassed
 └─ original_validation_id
```

하나의 테이블에서 다음 세 가지 역할을 수행한다.

1. 퀴즈 생성 요청 기록
2. AI 퀴즈 생성 진행 상태 관리
3. 생성 완료된 퀴즈 리소스 저장

이에 대해 생성 요청 이력과 실제 퀴즈 데이터를 분리하는 것이 실무적으로 더 적합하다는 의견이 제시되었다.

제안 구조:

```
quiz_generation_request
 ├─ id
 ├─ content_id
 ├─ status
 ├─ requested_at
 ├─ completed_at
 └─ error_code

        ↓ 성공 시

quiz_set
 ├─ id
 ├─ request_id
 ├─ content_id
 ├─ question_count
 ├─ created_at
 ├─ is_bypassed
 └─ original_validation_id
```

이 구조에서는 실패한 생성 요청은 Request 테이블에서 관리하고, 실제 생성 완료된 퀴즈만 `quiz_set`에 저장한다.

## 결정

현재 Readle v0.7에서는 **`quiz_set`과 퀴즈 생성 요청 이력을 별도 테이블로 분리하지 않고 유지한다.**

즉, 현재 구조를 유지한다.

향후 다음 요구사항이 추가되는 경우 `quiz_generation_request` 테이블을 별도로 도입하는 방향으로 확장한다.

- 사용자 반복 생성 요청 관리
- AI 생성 실패 재시도 관리
- AI 호출 비용 및 토큰 사용량 추적
- 비동기 Queue 기반 생성 Job 관리
- 생성 요청 모니터링 및 운영 로그 관리

---

## 이유

현재 Readle의 요구사항은 "콘텐츠를 기반으로 AI가 퀴즈를 생성한다"는 수준이며, 생성 요청 이력 자체를 별도로 조회하거나 운영할 요구사항은 존재하지 않는다.

또한 현재 `quiz_set.status`를 통해 다음 상태를 충분히 관리할 수 있다.

```
GENERATING → COMPLETED
              ↓
            FAILED
```

따라서 현재 규모에서는 별도의 Request 테이블을 추가하는 것이 아래와 같은 비용을 발생시킨다.

- ERD 복잡도 증가
- 테이블 간 관계 증가
- 관리해야 할 도메인 개념 증가

반면 `quiz_set`에서 생성 상태를 함께 관리하면 초기 서비스 단계에서 구현 복잡도를 낮추면서도 필요한 상태 관리는 가능하다.

다만 실무 환경에서는 생성 요청과 결과 데이터를 분리하는 구조가 더 적합하다.

그 이유는 다음과 같다.

### 1. 실패 요청과 실제 퀴즈 데이터의 역할 분리

현재 구조에서는:

```
quiz_set

id | content | status
----------------------
1  | A       | FAILED
2  | A       | COMPLETED
```

처럼 실패한 생성 요청도 퀴즈 데이터 테이블에 저장된다.

따라서 `quiz_set`이 "생성 요청"인지 "완성된 퀴즈"인지 역할이 모호해질 수 있다.

분리 구조에서는:

```
quiz_generation_request

1 | A | FAILED
2 | A | COMPLETED

quiz_set

101 | A | 생성 완료된 퀴즈
```

처럼 책임이 명확해진다.

---

### 2. 재생성 이력 관리 용이

같은 콘텐츠에 대해 여러 번 퀴즈 생성을 요청하는 경우:

현재 구조:

```
quiz_set

1 | content A | FAILED
2 | content A | COMPLETED
3 | content A | COMPLETED
```

생성 이력인지 실제 퀴즈인지 구분이 필요하다.

분리 구조:

```
quiz_generation_request

1 | A | FAILED
2 | A | COMPLETED
3 | A | COMPLETED

quiz_set

101 | request 2
102 | request 3
```

요청과 결과의 관계가 명확하다.

---

### 3. AI 서비스 운영 데이터 확장 가능

향후 AI 기능 운영 시 생성 요청 단위로 다음 데이터를 관리할 필요가 있다.

```
quiz_generation_request

id
content_id
status
model_name
prompt_version
token_usage
error_code
requested_at
completed_at
```

이는 AI 비용 관리 및 장애 분석에 활용 가능하다.

---

## 고려한 대안

### 대안 1. 현재 구조 유지 (`quiz_set`에서 생성 상태 관리)

**장점**

- 구조가 단순함
- ERD 복잡도가 낮음
- 현재 요구사항에 충분함
- 구현 비용이 낮음

**단점**

- 생성 요청과 완료된 퀴즈 데이터의 책임이 혼합됨
- 실패 요청 이력이 `quiz_set`에 누적됨
- AI 운영 로그 확장성이 낮음

---

### 대안 2. `quiz_generation_request` 테이블 추가

```
quiz_generation_request
        |
        ↓
    quiz_set
```

**장점**

- 요청과 결과 데이터 책임 분리
- 생성 실패 이력 관리 가능
- 재생성 흐름 표현이 명확함
- AI 운영 데이터 확장 가능

**단점**

- 테이블 및 관계 증가
- 현재 요구사항 대비 과도한 설계 가능성 있음
- 초기 개발 복잡도 증가

---

## 결론

현재 Readle의 범위에서는 `quiz_set`을 유지하는 방향으로 결정한다.

현재 요구사항에서는 생성 상태 관리만으로 충분하며, 별도의 요청 이력 관리 요구사항이 없기 때문에 `quiz_generation_request`를 추가하는 것은 과설계에 해당한다.

다만 향후 AI 생성 기능이 확장되어 다음 요구사항이 발생할 경우 Request 테이블 분리를 적용한다.

- 생성 요청 이력 관리
- AI 호출 로그 관리
- 실패 재시도 관리
- 비동기 생성 Job 관리
- 비용 및 운영 데이터 추적

따라서 현재 설계는 MVP 단계에 적합한 구조이며, 서비스 확장 시 자연스럽게 분리 가능한 구조로 판단한다.

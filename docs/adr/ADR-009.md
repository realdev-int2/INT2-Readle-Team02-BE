# ADR-009: 퀴즈 대기 상태 조회를 위해 Short Polling을 채택한다

## 상태

Accepted

## 배경

사용자가 아티클 콘텐츠를 제출하면 비동기 백그라운드 스레드에서 `크롤링 ➔ AI 기술 검증 ➔ 퀴즈 생성` 파이프라인이 구동된다. 이 과정에서 사용자는 최종 생성 완료 시점까지 약 10초 내외의 대기 지연(Latency) 시간을 겪게 된다.
대기 상태를 클라이언트에 전달하는 실시간 연동 방식이 요구되나, 현재 프로젝트는 다음과 같은 강력한 환경적 제약 사항을 수반한다.

- **한정된 개발 일정**: 실제 기능 구현에 할당된 프론트엔드/백엔드 개발 기간이 2~3주 내외로 매우 타이트함.
- **인프라 자원 제한**: RAM 4GB 단일 EC2 내에 Nginx, MySQL, Redis, 백엔드, 프론트엔드가 모두 Docker 이미지로 구동되어야 하므로, 메모리 및 스레드 풀 등 커넥션 점유 리소스를 최소화해야 함.
이에 따라 사용자의 대기 화면(단일 로딩 화면 및 단계 노출)에서 퀴즈 생성 완료 여부를 감지하기 위한 API 아키텍처 설계에 대해 논의를 거쳤다.

## 결정

퀴즈 대기 및 진행 상태 조회 API에 실시간 스트리밍 프로토콜(WebSocket, SSE) 도입을 MVP 범위 외로 전면 제외하고, **3초 주기의 단기 폴링(Short Polling)** 방식을 채택한다.

- 클라이언트는 3초 주기로 `GET /contents/{contentId}/validation` 엔드포인트를 호출하여 비동기 작업 상태를 수집한다.
- 상태가 완료(`passed`로 인한 퀴즈 생성 완료)되거나 실패(`rejected` 또는 `failed`)로 변경되면 폴링 인터벌을 즉시 중단(Clear Interval)하고 후속 UX 흐름을 처리한다.

## 이유

1. FE/BE 개발 공수 감소 (2-3주의 타이트한 일정)

- 웹소켓(WebSocket)이나 SSE(Server-Sent Events)를 도입할 경우 프로토콜 업그레이드, 재연결(Reconnect), 하트비트(Heartbeat) 등 프론트엔드와 백엔드 양측에 추가적인 개발 및 관리 리소스 소요가 큼.
- 반면, 폴링 방식은 표준 HTTP GET API를 주기적으로 호출하기만 하면 되므로, 2~3주의 한정된 개발 일정 안에서 구현과 디버깅 생산성을 극대화할 수 있음.

2. 단일 EC2 인프라 리소스 보존 (비용/스레드 자원)

- 웹소켓이나 SSE는 AI 연동 대기 시간 동안 클라이언트와 서버 간의 지속적인 커넥션(Persistent Connection)을 유지해야 하므로, MVP용 소형 단일 EC2 서버의 소켓 및 스레드 풀 리소스 점유 부하가 가중됨.
- 반면, 폴링 방식은 무상태(Stateless) 단발성 요청이므로 불필요한 지속 연결 자원 낭비를 원천적으로 방지할 수 있음.

3. 짧은 대기 시간 대비 효율성 (오버엔지니어링 방지)

- 콘텐츠 검증 및 퀴즈 생성에 소요되는 시간은 평균 10초 내외임. 3초 주기로 조회하더라도 단 3~4회의 가벼운 API 호출로 상황이 종료됨.
- 이처럼 짧은 대기 시간을 해결하기 위해 웹소켓 서버를 셋업하고 로드밸런서 설정을 구성하는 것은 MVP 범위에 비해 불필요하게 복잡한 오버엔지니어링에 가깝다고 판단됨.

## 고려한 대안

### WebSocket (양방향 연결) 도입

장점:

- 검증 및 생성 완료 시점의 이벤트를 밀리초(ms) 단위의 지연 없이 즉각적으로 전달 가능함.

단점:

- 프론트/백엔드 모두 핸드셰이크 및 에러 처리 구현이 복잡함.
- 단일 EC2 환경에서 동시 접속 시 Persistent Connection 유지에 따른 리소스 고갈 위험이 큼.

### SSE (Server-Sent Events) 도입

장점:

- 웹소켓에 비해 HTTP 프로토콜 상에서 작동하므로 가볍고 백엔드 단방향 푸시에 적합함.

단점:

- HTTP/1.1 환경에서 브라우저당 커넥션 수 제한(최대 6개) 문제 및 커넥션 끊김 시 재연결 제어가 필요함.
- 여전히 지속 연결을 유지해야 하므로 서버 스레드 점유 리스크가 존재함.

### Short Polling (단기 폴링) 도입

장점:

- 가장 단순한 HTTP GET 호출로 즉시 구현할 수 있음.
- 무상태 요청이므로 서버 측 지속 세션 자원 관리가 불필요함.

단점:

- 3초 단위 호출 사이의 딜레이(평균 1.5초의 감지 지연)가 존재하며, 호출 횟수만큼 HTTP 헤더 오버헤드가 발생함. (단, 10초 내외의 시간 동안 3~4회 호출에 불과하므로 무시할 수 있는 수준임.)

## 결과

- MVP 적용: `GET /contents/{contentId}/validation`을 3초 주기로 호출하는 Short Polling으로 최종 구현한다.
- 롤백 및 예외 관리: 폴링 도중 예외 에러(500)가 수신되거나 최종 실패 상태가 수집되면, 폴링을 즉시 해제하고 에러 피드백을 노출한다.

추후 재검토:

- 추후 사용자 규모가 확장되어 폴링 요청으로 인한 서버 트래픽이 임계치를 초과하는 경우.

- 더 복잡한 AI 추론 파이프라인의 연계로 평균 대기 시간이 30초 이상으로 크게 늘어날 경우, SSE(Server-Sent Events)로의 전환을 재검토하는 의사결정 트리거를 발동한다.

# ADR-001: **적합성 검증은 서버 규칙 가드레일과 AI 구조화 판정 결합으로 도입한다**

## 상태

Accepted

## 배경

사용자 입력 또는 콘텐츠에 대한 적합성 검증이 필요하다.

초기 논의에서는 별도 임베딩을 사용하지 않고 AI API를 호출해 다음 값을 한 번에 응답받는 방향을 검토했다.

- 적합성 점수
- 통과 여부
- 반려 시 거절 사유 또는 상세 설명

이 방향은 p95 기준 5초 이내 응답이면 AI API 호출 지연을 허용할 수 있고, 임베딩 기반 구현보다 단순하다는 판단에 기반했다.

하지만 이후 논의에서 AI에게 사용자 노출용 상세 설명(detail) 생성을 위임하는 구조가 위험할 수 있다는 의견이 있었다. AI가 원문이나 정책에 근거하지 않은 설명을 생성하면 할루시네이션이 발생할 수 있기 때문이다.

반대로 detail을 AI가 생성하지 않는다면, 점수 계산과 reject_reason_code 산출만을 위해 AI API를 호출하는 것이 응답 시간 증가를 정당화할 수 있는지도 검토해야 한다.

## 초기 논의 방향

- AI API는 자연어 detail을 생성하지 않는다.
- AI API는 구조화된 판정값만 응답한다.
    - `status`
    - `score`
    - `reject_reason_code`
    - 필요 시 원문 근거 확인용 `evidence_quote`
- ~~기존 기획서의 검증 응답 필드명과 맞추기 위해 `status`, `score`, `reason_code`를 canonical schema로 사용한다. `reject_code`로의 명칭 변경이 필요하면 별도 논의한다.~~
- 사용자에게 노출되는 detail은 서버에서 `reject_reason_code`별 고정 문구로 매핑한다.
- AI 응답은 스키마 검증을 통과한 경우에만 사용한다.
- 서버는 최종 판정의 권한을 가진다. AI 응답의 `score`, `status`, `reject_reason_code`가 서로 충돌하면 서버의 우선순위 규칙과 fallback 정책으로 정규화한다.
- 필드 충돌 시 정확한 우선순위 테이블은 추후 확정하되, MVP 구현 전 서버 정의 우선순위 규칙을 명시해야 한다.
- 스키마 검증 실패, 알 수 없는 `reject_reason_code`, 응답 중단, 필드 간 충돌 등은 안전한 기본 반려 또는 재시도로 처리하고 로그를 남긴다.
- `evidence_quote`는 원문 포함 여부를 기계적으로 검증하지 않는 한 사용자에게 노출하지 않는다. 기본 용도는 내부 디버깅과 품질 점검으로 제한한다.
- 임베딩 또는 RAG는 정책, 예시, 문서 corpus 기반의 grounding이 필요해질 때 재검토한다.

## 이유

- 구조화 출력은 응답 형식과 허용 필드를 통제하는 데 적합하다.
- 자연어 detail의 사실성과 근거성은 스키마만으로 보장하기 어렵다.
- 사용자 노출 문구를 서버에서 고정하면 할루시네이션 위험과 표현 일관성 문제를 줄일 수 있다.
- AI는 개발 관련성 같은 의미 판단에 집중하고, 사용자-facing 문구와 최종 fallback은 애플리케이션이 통제할 수 있다.
- `evidence_quote`도 검증 없이 노출하면 또 다른 자연어 truth surface가 되므로 기본적으로 내부용으로 제한한다.
- 임베딩은 유사 문서 검색과 grounding에는 유용하지만, 단순한 detail 생성 할루시네이션 방어의 1차 해법은 아니다.
- MVP에서는 임베딩 저장소와 유사도 검색 인프라를 추가하기 전에 구조화 AI 판정과 서버 고정 문구로 충분한지 검증하는 편이 단순하다.

## 고려한 대안

### 1. AI API가 점수, reject_reason_code, detail을 모두 응답

AI가 적합성 점수, 통과 여부, reject_reason_code, detail을 모두 생성하는 방식이다.

장점:

- 구현 흐름이 단순하다.
- AI가 판단 컨텍스트를 바탕으로 반려 사유를 바로 설명할 수 있다.
- 별도 문구 매핑 테이블이 없어도 된다.

단점:

- detail에서 할루시네이션이 발생할 수 있다.
- 사용자에게 부정확하거나 일관되지 않은 반려 사유가 노출될 수 있다.
- 응답 형식을 고정하더라도 자연어 내용의 사실성까지 보장하기 어렵다.
- 프롬프트 또는 정책 변경에 따라 사용자-facing 문구가 흔들릴 수 있다.

### 2. AI API는 구조화된 판정값만 응답하고 detail은 서버에서 매핑

AI가 자연어 detail은 생성하지 않고, 적합성 점수와 reject_reason_code 등 구조화된 값만 응답하는 방식이다.

장점:

- 사용자 노출 문구를 deterministic하게 관리할 수 있다.
- 자연어 detail 할루시네이션 위험을 줄일 수 있다.
- AI는 의미 판단에만 사용하고, 표현은 애플리케이션이 통제한다.
- 임베딩 인프라 없이도 MVP에서 검증 가능하다.

단점:

- reject_reason_code taxonomy와 고정 문구를 설계해야 한다.
- 필드 간 충돌과 실패 응답에 대한 서버 fallback 정책이 필요하다.
- reject_reason_code 판단 오류 가능성은 남는다.
- AI API 호출로 인한 응답 시간과 비용은 여전히 발생한다.
- 고정 문구만으로 충분히 구체적인 피드백을 제공하지 못할 수 있다.

### 3. 규칙 기반으로 점수와 reject_reason_code 산출

AI API를 호출하지 않고 애플리케이션 코드에서 규칙 기반으로 판단하는 방식이다.

장점:

- 응답 시간이 짧다.
- 결과가 재현 가능하다.
- detail을 고정 문구로 제공하기 쉽다.
- AI API 비용이 발생하지 않는다.

단점:

- 개발 관련성 같은 의미 판단에는 한계가 있을 수 있다.
- 규칙 설계와 유지보수가 필요하다.
- 초기 규칙 품질에 따라 오탐 또는 미탐이 발생할 수 있다.

### 4. 임베딩 또는 RAG 기반 적합성 검증

콘텐츠나 정책 문서를 임베딩하고, 유사도 검색 또는 검색 증강 생성을 통해 적합성을 판단하는 방식이다.

장점:

- 정책, 예시, 문서 corpus가 많아질 때 관련 근거를 검색해 사용할 수 있다.
- 특정 기준 문서에 grounded된 판단이 필요할 때 유용하다.
- 유사 콘텐츠나 기준 사례를 활용할 수 있다.

단점:

- 임베딩 생성, 저장소, 유사도 검색 인프라가 필요하다.
- 검색 결과 품질과 임계값 보정이 필요하다.
- MVP 대비 구현 복잡도가 크다.
- detail 할루시네이션 방어만을 위한 1차 해법으로는 과할 수 있다.

## 추가 논의 필요 사항

최종 결정 전까지 다음을 확인한다.

- reject_reason_code 목록과 각 코드의 고정 detail 문구
- 점수 산정 기준과 통과 임계값
- AI 응답 스키마와 검증 실패 시 fallback 정책
- `score`, `is_valid`, `reject_reason_code`가 충돌할 때의 서버 우선순위 규칙
- `evidence_quote`를 받을 경우 원문 포함 여부를 서버에서 검증할지 여부
- invalid schema, unknown `reject_reason_code`, interrupted response, field conflict 케이스의 수용 기준
- p95 5초 기준 안에서 AI API 호출이 허용되는지
- 고정 문구만으로 사용자 피드백이 충분한지
- 임베딩 또는 RAG가 필요한 정책 corpus가 실제로 존재하는지

## 결과

7/8 3차 기획 논의

**서버의 규칙 필터**와 **AI의 구조화 판정**을 결합한 하이브리드 검증 방식을 채택한다.

1단계 규칙 검증 가드레일을 도입하여 프론트엔드 검증 우회 요청을 서버 단에서 정규식 및 초성 필터링으로 0ms 즉시 차단 처리한다.

이를 통과한 콘텐츠에 한해서만 2단계 AI 구조화 판정을 진행하며, AI는 자연어 detail을 생성하지 않고`is_valid` , `score`, `reject_reason_code`, `evidence_quote` 구조화 데이터만 응답한다.

상세 반려 사유(detail)는 서버에서 reject_reason_code별 고정 문구와 AI가 제공한 evidence_quote(인용구/키워드)를 조립하여 최종 상세 문구를 만들어 사용자에게 힌트 형태로 제공한다.

사용자 대기 시간을 제거하기 위해 등록은 즉시 완료시키고, 백그라운드 큐에서 비동기로 AI 검증을 수행하는 비동기 사후 검증 방식을 도입한다.

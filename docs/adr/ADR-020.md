# ADR-020: 커스텀 메트릭은 도메인 완료 경계에서 명시적으로 계측한다

## 상태

Accepted

## 배경

ADR-012에서 Micrometer, Prometheus, Grafana 기반의 모니터링 토폴로지를 결정했다. 이후 AI 호출, 콘텐츠 검증, 퀴즈 생성·채점의 성공·실패·재시도·처리 시간 등 비즈니스 메트릭이 필요해졌다.

이 흐름은 단순한 Spring 메서드 호출과 완료 경계가 일치하지 않는다. 비동기 완료, 타임아웃, 재시도, 상태 저장, 우회 생성 성공 여부가 각각 실제 결과를 결정한다.

## 범위

이 결정은 비즈니스 커스텀 메트릭에 적용한다. HTTP·JVM 등 Actuator 기본 메트릭과 ADR-012의 수집·저장·시각화 토폴로지는 변경하지 않는다.

## 결정

커스텀 메트릭은 각 도메인의 실제 완료 경계에서 명시적으로 기록한다. 현재 비즈니스 메트릭에는 범용 AOP 또는 `@Timed`를 사용하지 않는다.

- AI 호출은 Provider 호출 결과와 토큰 사용량이 확정된 시점에 기록한다.
- 콘텐츠 검증은 최종 검증 상태가 저장된 시점에 기록한다.
- 퀴즈 생성은 `QuizSet` 완료 또는 실패가 확정된 시점에 기록하며, bypass는 성공적으로 완료된 생성만 집계한다.
- 퀴즈 채점은 비동기 채점 완료와 결과 저장까지 끝난 시점에 기록한다.

단순하고 동기적으로 완료되는 공통 작업이 반복되며, 결과·상태·재시도 의미를 숨기지 않는 경우에만 AOP 도입을 재검토한다.

## 고려한 대안

### AOP 또는 `@Timed`

동기 메서드의 기본 처리 시간에는 적합하다. 그러나 현재 흐름의 비동기 완료, 재시도, 타임아웃, 동적 결과 태그와 저장 성공 여부를 정확히 표현하려면 Aspect에 도메인 정책을 다시 구현해야 한다. 이는 계측 위치를 감출 뿐 코드와 중복 집계 위험을 줄이지 못한다.

## 결과

계측 코드가 완료 경계 가까이에 남아 메트릭의 성공·실패 의미를 코드와 함께 검토할 수 있다. 완료 경계가 변경되면 해당 메트릭과 테스트도 함께 수정해야 한다.
